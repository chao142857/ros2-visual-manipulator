# 移动底盘：控制代码尚未接入本仓库

截至 2026-09-20 的仓库审计，本项目的可定位实现集中在六轴机械臂、二指夹爪、
RGB-D 感知、视觉抓取实验和 GUI。当前九个 ROS 2 package 中没有移动底盘驱动、
里程计或导航 package，也没有可用的底盘启动命令。**移动底盘集成仍在开发准备阶段，
本仓库不支持完整 autonomous mobile manipulation。**

用户已确认实物系统加入了底盘；这不等于其软件已集成。第二阶段扩大到限定开发目录，
结论为：**physical mobile base exists, but software integration is not present in inspected development directories**。
此结论不是全盘搜索结果，也不判断未检查存储位置或实物独立运行能力。
现有机械臂/感知数据流见 [architecture.md](architecture.md)。

## TF 接入前必须解决的语义

现有 `arm_description/urdf/dummy-v1.urdf` 与 `dummy-v2.urdf` 都以 `base_link` 为
机械臂根。V2 URDF 声明的链为（运行时 TCP 仍依赖缺少常规发布者的被动关节状态）：

```text
base_link（机械臂根）
├── tag0_ref
└── link1_1_1 → link2_1_1 → link3_1_1 → link4_1_1
    → link5_1_1 → link6_1_1 → tool0 → tcp
```

`tabletop_grasp/config/tabletop.yaml` 的 `base_frame`、ROI，以及 MoveIt arm 组和
既有标定引用，都依赖这个名称与含义。`tool0 → tcp` 还包含夹爪相关的被动伸长。
不能把 `base_link` 直接改成移动底盘根，也不能只重命名 URDF 而遗漏配置、目标位姿、
规划场景和标定引用。本次没有修改这些 frame、joint origin、axis 或标定值。

尚未发现已经接入的第二套底盘 TF，因此不能报告“当前底盘与机械臂 TF 已冲突”。
实际风险是未来集成时两套模型都使用 `base_link`、重复发布静态变换，或误用原有
机械臂基准坐标。接入前应完成以下合同：

1. 确认独立机械臂和整机模式各自的根 frame、命名方案及其唯一发布者。
2. 实测底盘到机械臂安装面的刚体变换；不从示意图、旧规划或视觉外观猜测数值。
3. 明确是否需要 `base_footprint`，并为 `map → odom`、里程计到车体根的边指定
   唯一发布者。原始轮式里程计与融合节点不能同时拥有同一条边。
4. 列出所有受迁移影响的消费者：URDF/SRDF、MoveIt、相机外参、手眼标定、ROI、
   目标位姿、GUI、RViz 和保存的数据。保留可回溯的旧坐标语义。
5. 在离线模型和隔离 mock 环境验证单父节点、单发布者、单位、方向与时间戳；
   比较迁移前后同一实体点的坐标变换结果，再安排现场标定验收。

目标是符合 REP-103/REP-105 的一致坐标约定。最终整机 TF 图必须由实际底盘、
安装几何和发布权确定，当前不把通用示意链当成已实现结构。

## 分阶段验收计划（本轮未执行）

### 1. 源码与无硬件检查

先读取实际驱动及所有启动/退出路径，确认构造函数、重连和退出是否写设备或发送
使能/速度命令。再进行依赖检查、语法检查、针对性构建和协议 fake/mock 测试。
mock 必须不打开真实设备；若使用 ROS，隔离 domain，并确认该域没有实体驱动。

| 检查 | 计划中的通过证据 |
| --- | --- |
| 协议解析 | 已知报文样本可重现；短帧、坏校验、错误单位、非有限值和未知状态被拒绝 |
| 命令时效 | 明确命令时间/接收时间语义；过期、乱序、异常时间与重连后的旧命令不自动执行 |
| 轮序与运动学 | 使用记录的轮序和几何生成离线样本，覆盖实际底盘支持的运动自由度 |
| 输出权限 | 无使能时拒绝运动；多个命令源的仲裁可解释，旧队列不会在重连后回放 |
| 故障与取消 | 注入反馈超时、通信断开、队列积压；记录状态迁移与拒绝原因 |

这些检查证明软件处理路径，不证明真实轮子方向、停止距离或底盘稳定性。

### 2. 反馈与里程计验收

先检查反馈读取本身是否包含隐式使能，再规划现场测试。只接受有时间戳且足够新鲜的
反馈，分别记录轮式里程计原始输出与融合输出。未知协方差不能以零值冒充无误差。

后续受监督实测需核对轮序/方向/单位，使用外部测量参考比较直行和转向的距离、角度、
漂移、重复性及打滑影响；如实际底盘支持横移，再增加横移项目。还需记录计数回绕、
重启/里程计归零与 TF 连续性的行为。可接受误差、测试距离和速度均为 TBD，必须由
实际工作区和硬件风险确定，不能在本文中编造阈值。

### 3. Watchdog 与停止验收

软件先用 mock 注入命令源消失、反馈失效、主机通信中断和重连。现场另行验证 MCU/
驱动器是否具备独立超时停止机制，以及主机崩溃、掉电和链路断开时的真实行为。
ROS 进程正常退出时发送零速度的清理代码，不能覆盖这些故障。

每个故障应记录触发时间、最后有效反馈、实际速度变化、停止时间/距离及恢复条件。
仅收到 ACK、看到零命令或节点退出，不足以判定物理停止。急停、制动和失能的语义
必须分别核实；轮子继续滑行或关节卸力等影响应进入整机风险记录。

### 4. 底盘停稳与机械臂互锁

先在隔离 mock 中验证未来协调器，再安排实机验收。计划合同如下，当前均未实现：

- 进入抓取前，底盘任务已结束或取消，命令权已释放；线/角速度命令和新鲜实测反馈
  均满足停稳条件，并保持经实测批准的时长。定位与反馈失效时禁止解锁机械臂。
- 停稳速度阈值、持续时间、允许漂移、臂收拢姿态和底盘净空要求均为 TBD。
  零 `cmd_vel` 或导航 action 成功不能单独作为停稳证明。
- 机械臂离开批准的移动姿态后，拒绝底盘运动请求；抓取期间持续检查底盘反馈，
  不能只在流程开始时检查一次。
- 感知、TF、底盘或机械臂故障时，停止后续步骤并进入明确的故障状态。恢复需要
  新鲜状态和受控确认，不自动回放导航目标、臂目标或夹爪命令。
- 首次集成采用“导航/人工定位 → 停稳 → 感知 → 规划 → 受控操作”的顺序。
  底盘与机械臂同时运动、全身规划均不在当前实现范围内。

每一阶段应独立记录源码/固件版本、测试输入、输出和失败处置。下一阶段开始前复查
上一阶段证据，不能把 mock、ROS 消息畅通或 RViz 显示升级为实体通过。

## 本轮安全边界

本轮底盘专项只进行了仓库与归档清单的静态调查，没有启动底盘节点、发送机械臂/夹爪/底盘
运动命令、写入真实串口、运行可能驱动硬件的 launch 或烧录固件。
本节所有涉及实物动作的验收计划状态为：

`SKIPPED: requires physical robot actuation`

实际底盘实现和现场验收资料接入前，不能用现有机械臂启动脚本组合出一个声称可用的
整机 bringup。实机边界与现有驱动风险见 [safety.md](safety.md)。
